# AIPE Workbench — 架构最小复现

一个 AI 后编辑（AI Post-Edit）翻译流水线的架构复现：上游推入待处理的
机器译文，平台逐句调用大模型做"保留或重译"的判定，结果落库并回调上游。

> **关于原项目**
>
> 原平台的代码、业务数据和客户信息归我实习的公司所有，不在本仓库公开。
> 这里复现的是**架构与调度机制本身** —— 三队列流水线、按 batch 大小的优先级
> 调度、上下文窗口、行内标签保真校验、事务边界。代码是重新写的，
> 不包含原项目的任何一行；示例数据是自编的通用界面文案。
>
> 复现的动机很直接：这些问题的解法是我在项目里真正负责的部分，
> 但它们的效果只有跑起来才看得见。

## 架构

```
                    ┌──────────────────┐
   上游业务系统 ────▶│  Producer (API)  │  校验 / 幂等去重 / 建任务 / 预算上下文
   (HMAC 签名)      └────────┬─────────┘
                             │ 每条 segment 一条消息（带优先级）
                             ▼
                    ┌──────────────────┐
                    │   MQ1 task       │  x-max-priority=10
                    └────────┬─────────┘
                             │
                  ╔══════════▼══════════╗   按队列积压量弹性伸缩
                  ║  Consumer Pods N    ║   （每副本目标积压 ≤ 10 条）
                  ║  拼 Prompt → 调 LLM ║   min 1 / max 50
                  ╚══════════╦══════════╝
                             │ 结果（含失败）
                             ▼
                    ┌──────────────────┐
                    │   MQ2 result     │
                    └────────┬─────────┘
                             ▼
                    ┌──────────────────┐
                    │   Writer         │  写 segment + 推进度（同一事务）
                    └────────┬─────────┘
                             │ 任务全部完结时
                             ▼
                    ┌──────────────────┐
                    │   MQ3 callback   │  隔离慢路径：HTTP 回调 + 退避重试
                    └────────┬─────────┘
                             ▼
                    ┌──────────────────┐
                    │   Callback       │
                    └──────────────────┘

                    MQ1 ──超时/重投超限──▶ DLQ ──▶ 标记 segment timeout
```

三条队列分开的理由：每一段的耗时特征不同。把 LLM 调用、数据库写入、
HTTP 回调混在一条队列里，慢环节会把快环节一起拖住 —— 这是踩过的坑。

## 三个演示，都是实跑输出

### 1. 队列饥饿：为什么队列需要优先级

一个真实事故的复现。上游同时推来一个大任务和若干小任务，
队列是严格 FIFO 的，大任务的消息先入队把队列占满，小任务全部饿死。

`run_scheduling_demo.py` 用**同一份代码**跑两种模式，唯一差别是消息优先级：

```
[模式 A] 严格 FIFO —— 所有消息同优先级
  队列中消息数 890（大任务 790 + 小任务 20 x 5），单 consumer 串行处理
  大任务 (790 段)   完成于 11.74s
  小任务 (20 个)   平均等待 12.54s  (最快 11.82s / 最慢 13.24s / p95 13.17s)

[模式 B] 优先级队列 —— 按 batch 大小分级 (<=5->10, <=20->8, <=100->6, <=500->4, <=inf->2)
  大任务 (790 段)   完成于 13.40s
  小任务 (20 个)   平均等待 0.77s  (最快 0.08s / 最慢 1.48s / p95 1.40s)

对照结论
  小任务平均等待 : 12.54s  ->  0.77s    （下降 93.9%）
  小任务 p95 等待: 13.17s  ->  1.40s    （下降 89.3%）
  大任务总耗时   : 11.74s  ->  13.40s   （变化 +14.1%）
```

代价是明确的：大任务晚完成 14%。但大任务本身是批处理，晚一秒没有业务影响；
小任务晚一秒，上游看到的是"我推了一小批，十几秒了还没回来"。

优先级规则按 batch 大小分档，不是拍脑袋定的 —— 越大的任务让路成本越低，
越小的任务等待感知越强。实现上用的是 broker 原生优先级队列而不是应用层排序，
这样多副本消费时顺序依然成立。

> **部署坑**：已经在跑的队列不能直接加 `x-max-priority`，broker 会拒绝声明。
> 必须停服、删掉原队列、带参数重建。这一步在测试环境没问题，
> 在生产上会丢队列里的存量消息，必须等队列排空再操作。

### 2. 事务边界：progress 为什么会永远差 1

第二个真实事故。writer 处理完一条 segment 要做两件事：写结果、推进度。
如果这两件事各自提交，一旦在中间挂掉，结果写了、进度没动 ——
于是 progress 永远停在 `total-1`，任务永远不会被判定为完成。

`run_transaction_demo.py` 把两条路径并排跑：

```
[路径 A] 单事务：segment 写入 + 进度推进 一起提交
  segments done : 12 / 12
  progress      : 12 / 12
  status        : done
  reaper        : DONE

[路径 B] 两次提交：各自成事务，在最后一条的两次写入之间模拟进程崩溃
  segments done : 12 / 12   ← 数据其实全跑完了
  progress      : 11 / 12   ← 计数永远差 1
  status        : queued    ← 任务永不结束
  reaper        : REAP（停滞 1805 秒 > 阈值 1800 秒）
```

出故障之前，两条路径的表现完全一样 —— 这就是这类 bug 难发现的地方，
它只在异常路径上出现。

修复是合并成单事务。同时有两条配套规则：

- **MQ publish 要放在事务之外**。先 publish 再提交事务的话，
  事务回滚后消息已经发出去了，消费者会取到一条指向不存在数据的消息。
- **收尾判定不能只看计数**。可能有 segment 进了 DLQ 永远回不来，
  那样计数永远差几条。要补一条"还有没有非终态 segment"的检查，
  没有就强制收尾，并在回调里说明哪些失败了 ——
  上游宁可拿到部分结果加失败明细，也不愿意一直等到超时。

### 3. 完整流水线

```
submit_batch -> {'task_id': 'demo-batch-001', 'accepted': True, 'total': 120, 'priority': 4}

RESULT
  status        : done
  progress      : 120 / 120
  failed        : 0
  elapsed       : 2.64 s
  throughput    : 45.4 segment/s
  evaluation Y/N: 88 / 32
  tag mismatch  : 26
  callbacks     : 1
  callback body : {"task_id":"demo-batch-001","status":"done","progress":120,"total":120,"failed":0}
```

120 条里 32 条被判 `N`（需要重译），其中 26 条是行内标签对不上。
这不是模型不听话，是机器译文的常态 —— 所以标签校验必须是**代码检查**，
不能靠 Prompt 里叮嘱模型注意格式。

## 行内标签保真

译文最终要回写进下游翻译系统渲染，所以译文里的行内占位符
必须与原文一一对应。做法参考 MXLIFF 规范的四条约束：

| 约束 | 说明 |
|---|---|
| 数量一致 | `{1}{2}` 不能在译文里变成 `{2}` |
| 编号集合一致 | 数量对但编号变了同样不接受 |
| 开闭配对一致 | `<b>...</b>` 的嵌套结构不能被破坏 |
| 转义形式一致 | 原文是 `&amp;` 就不能在译文里变成 `&` |

位置**可以**变 —— 目标语言的语序不同，这是正常的。所以比较的是集合与结构，
不是顺序。`tests/test_pipeline.py::TestTagValidation` 覆盖了这几种情况。

## 上下文窗口

上游给的是逐句机器译文，一句一句独立丢给模型会断开指代和语气。
做法是给目标句配一个滑动窗口（前后各 N 条），并在 Prompt 里明确标出
哪一条才是要处理的。

`is_self` 这个标记看着不起眼，但缺了它模型会把上下文里的句子也翻一遍，
造成重复输出。窗口尺寸是可配的，不是越大越好 —— 它直接决定 token 成本和延迟。
