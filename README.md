## 项目是做什么的

翻译行业的交付流程原本是「机器翻译 → 人工逐句校对」。
客户下调报价后，逐句人工校对的成本模型不再成立，业务方转向
**AI 后编辑**：在机器译文基础上，由模型判断哪些译文可以直接用、
哪些需要重新生成，翻译人员从"逐句改写"转为"抽查复核"。

平台要解决的就是这条流水线的工程问题：

- 上游业务系统按批次推入待处理的机器译文（单批最多 2000 段）
- 平台逐段调用模型做「保留 / 重译」判定，并把结果落库
- 上游通过签署的回调地址拿到完成通知，也可随时轮询任务状态

实际运行规模：**数十个 program、数百个语言对**，
每个语言对绑定各自的风格指南与术语表，且语言对数量在持续增长。

## 架构要点

```
上游 → Producer → MQ1 → Consumer ×N → MQ2 → Writer → MQ3 → Callback → 上游
                     ↑ 按队列积压量弹性伸缩    ↑ 单事务写结果+进度   ↑ 隔离慢路径
```

四条经验是这个项目最主要的产出，每条都有事故背景：

| 结论 | 背景 |
|---|---|
| 多生产者写同一队列时，**FIFO 不是公平调度** | 大任务占满队列，一个时段内 **79 个小任务全部饿死**（占当时段 35%） |
| 写结果与推进度**必须同事务** | 两步各自提交，中断后进度永远差 1，**一天命中 9 个任务** |
| 多副本环境的**超时阈值依赖业务形态** | 30 分钟阈值在小批量时代合理，大批量出现后变成必然误杀 |
| 长连接 + 单例客户端**必须能自愈** | 一次连接失效导致 API 服务连续 503 直到手动重启 |

## 跑一遍复现

零外部依赖（内存队列 + SQLite + 规则式假模型），标准库就够：

```bash
cd demo
python run_pipeline.py          # 完整流水线：120 段 / 4 消费者
python run_scheduling_demo.py   # 调度对照实验：FIFO vs 优先级队列
python run_transaction_demo.py  # 事务边界：两条路径并排对照
python tests/test_pipeline.py   # 19 个单元测试
```

调度对照实验的实跑输出：

```
小任务平均等待 : 12.54s  ->  0.77s    （下降 93.9%）
小任务 p95 等待: 13.17s  ->  1.40s    （下降 89.3%）
大任务总耗时   : 11.74s  ->  13.40s   （变化 +14.1%）
```

大任务晚完成 14% 是明确代价 —— 但大任务是批处理，晚十几秒无感；
小任务晚十几秒，上游会认为系统挂了。这笔交易的判断依据写在这里。

想接真实 broker：`demo/docker-compose.yml` 提供 RabbitMQ 环境，
管理台里可以直接看到 `x-max-priority=10` 和死信队列的堆积情况。
