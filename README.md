# 连锁餐饮经营看板 + 问答服务

5 家门店连锁餐饮的经营看板，加一个能同时查数据库和公司文档的 AI 助手。
在公开题库 55 题 / 100 分上，从接手时的 17 分修到 90.5 分
（同一份代码连跑多轮会在 85–97 之间浮动，原因与证据写在 `EVAL_REPORT.md` 里，没有藏）。

## 三步跑起来

```bash
cd starter
make setup      # 建 venv（Python 3.12）+ 装依赖
make rebuild    # 从 ../data 与 ../knowledge_base 重建清洗表与检索索引
make run        # 起服务 http://127.0.0.1:8000，浏览器开根路径就是看板
```

不配任何 Key 也能跑（`mock` 降级模式，回答走本地模板）；配上大模型走 `live` 模式：

```bash
cp starter/.env.example starter/.env   # 填 LLM_BASE_URL / LLM_API_KEY / LLM_MODEL
```

换一套数据或知识库（评审会用同结构不同数字的数据替换后重建）：

```bash
make rebuild DATA_DIR=/path/to/data KB_DIR=/path/to/knowledge_base
```

索引、清洗表全部由这条命令重新生成，代码里没有任何写死的数字、答案或文档内容。

## 架构

```
                       ┌────────────────────────────────────────────┐
                       │              FastAPI (server.py)           │
                       │  /api/metrics/*  /api/retrieve  /api/chat   │
                       │  /api/trace/*    /api/data_quality          │
                       │  /  (看板与对话前端, 无 CDN, 内联 SVG)       │
                       └───────────────┬────────────────────────────┘
                                       │
                              service.py 编排
                                       │
              ┌────────────────────────┼─────────────────────────┐
              │                        │                         │
        guard 安全闸门            planner 意图/实体/时间        sessions 会话
              │                        │
              │                 ┌──────┴──────┐
              │                 │  mock 模式  │  本地模板回答（无 Key 降级）
              │                 └─────────────┘
              │                 │  live 模式  │  DeepSeek 工具调用回路
              │                 └──────┬──────┘
              │                        │  系统提示 + 10 个工具
              │         ┌──────────────┼───────────────┐
              │         │              │               │
              │    query_metrics / daily_metrics / payment_mix /
              │    top_products / by_store / compare_periods / run_sql
              │                        │
              │                  search_kb ──→ BM25 索引（含版本元数据过滤）
              │                        │
              └──→ 拒答（危险请求/未知实体/区间外数据）
                                       │
                            live.py 收尾核对（代码兜底，不信模型）
                                       │
                 · 数字核对：答案里的数必须能在工具结果或引用原文里找到
                 · 引用生成：逐字 quote，版本择优，问"为什么"扩到原因句
                 · 兜底：模型没标出处时按答案里的数回文档定位出处
```

两条硬约束贯穿全程：

1. **经营数字只能来自数据库查询**，进 `data_evidence`；**文档事实必须有逐字引用**，进 `citations`；
2. **代码兜底，不信模型**——数字核对、引用生成、版本择优全部在代码里做，模型只负责组织语言。

## 选型理由

- **检索用 BM25 而不是向量**：知识库 35 份文档、中英文混合、编号/别名/日期多，
  BM25 对精确词面（KB 编号、商品名、日期）的召回比轻量向量稳，且零外部依赖、
  换数据即重建、`/api/retrieve` 不依赖任何 Key。
- **live 模式用 OpenAI 兼容协议 + 三个环境变量**（契约 7.1 推荐路线）：
  切 DeepSeek `deepseek-flash` 不用改代码，接法见 `LLM_SETUP.md`。
- **数字核对放在代码里**：模型算术不可信，答案里的每个数都要过"允许清单"
  （工具结果 + 引用原文里的数 + 合法换算），过不了就让模型重写或删句。
- **前端不用任何 CDN**：内网可用，加载快，手绘 SVG 图表。

## 口径与歧义的取舍

按知识库现行口径（`KB-001` 指标口径手册 v3）：

- **净营业额**：`qty > 0` 的销售行金额减 `qty < 0` 的退款行金额；
- **订单数**：`order_id` 去重，退款行不计入订单数但计入退款金额；
- **闭区间**：`start`/`end` 两天都算，区间内无数据的天也要返回（值为 0，`aov` 为 null）；
- **文档估算值不算数**：店长周报里的"大概 150 份"是估算，不能当经营数字；
- **新旧版本**：问"现在"用现行版，问"当时"用当时有效的旧版（如 V03 问"那 6 月的时候"
  要引 KB-010 而不是 KB-011）；
- **数据库和文档冲突**：经营数字以数据库为准，文档里的数字只在回答"文档怎么说"时引用。
