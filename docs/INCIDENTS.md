# 事故复盘

三次故障的完整记录。选这三条的理由：它们都不是"写错一行代码"，
而是**设计层面的缺陷**，在不触发条件的时候看起来完全正常。

原始项目的内部文档用的是「症状 / 根因 / 修复 / 防再犯」四段式。
这里保留同样的结构，去掉了内部标识（客户业务线、环境地址、账号）。

---

## 事故一：队列饥饿 —— 小任务饿死在大任务后面

**发生时间**：2026-06-22 下午，持续约 2 小时 20 分钟
**影响**：一个时段内 **79 个任务失败**，占当时段总量的 **35%**

### 症状

失败模式高度一致，分三类：

| 类型 | 数量 | 特征 |
|---|---|---|
| 早期心跳超时 | 17 个 | 全部 `progress = 0/N`，**全程零进展**，存活时间恰好等于 reaper 阈值 |
| 进程重启 | 25 个 | 落在两次 Pod 重启窗口内 |
| 重启后心跳超时 | 一批 | Pod 重启后消费链路未恢复的窗口内 |

最扎眼的是第一类：任务从排队到被杀，**一段都没处理**。进程活着、心跳正常、
队列里有消息，但就是轮不到它。

### 根因

队列是 RabbitMQ 默认的 FIFO 队列。

触发条件是这样凑齐的：
- 某业务线同时推来 **6 个大任务，每个 790 段**，合计 4740 段
- 该业务线的 prompt 模板约 25 万字符，**单段 LLM 调用平均 ~9 秒**
- 集群吞吐约 **0.9 段/秒** → 4740 段需要约 **88 分钟**才能消化完
- 而这 6 个大任务的消息**先入队**，把队列占满了

之后推上来的小任务（1-6 段），消息必然排在那 4740 条后面。
reaper 的阈值是 30 分钟，远小于排空时间 —— **小任务必死，没有例外**。

### 为什么之前没暴露

大 batch 是后来才出现的业务形态。早期单次推送普遍在 20 段以下，
单任务 1-3 分钟跑完，队列从来不会积压到需要排队的程度。
业务侧开始推上百段的大批量之后，这个缺陷才稳定可见。

**这是架构缺陷，不是偶发 bug** —— 只要"小任务与大任务混跑"持续存在，
它就会反复出现。

### 修复

改用 RabbitMQ 原生优先级队列，按 batch 大小分档：

| batch 段数 | 优先级 |
|---|---|
| ≤ 5 | 10 |
| ≤ 20 | 8 |
| ≤ 100 | 6 |
| ≤ 500 | 4 |
| > 500 | 2 |

分档逻辑不是拍脑袋：**越大的任务让路成本越低**（它本来就是批处理，
晚几秒无感），**越小的任务等待感知越强**（上游盯着一个几段的小批次等）。

三个容易漏的实现细节：

1. **重试队列也要加同样的优先级参数**。否则消息进重试队列时默认
   `priority=0`，dead-letter 回主队列后优先级被抹掉，小任务又被降级。
2. **priority 要同时写进消息 body 和 AMQP BasicProperties**。
   消费者重投时需要从 body 里读出来重新设置。
3. 结果队列也一并加了优先级 —— 否则大任务的结果会把小任务的结果
   压在后面，落库延迟依然存在。

**效果**（`demo/run_scheduling_demo.py` 是用同一份代码做的对照实验）：

```
小任务平均等待 : 12.54s  ->  0.77s    （下降 93.9%）
小任务 p95 等待: 13.17s  ->  1.40s    （下降 89.3%）
大任务总耗时   : 11.74s  ->  13.40s   （变化 +14.1%）
```

大任务晚完成 14% 是明确的代价，也是这个方案成立的前提：
**大任务是批处理，晚十几秒没有业务影响；小任务晚十几秒，上游会认为系统挂了。**

### 部署陷阱

RabbitMQ **不允许给已存在的队列追加 `x-max-priority` 参数**，
声明时会直接报 `PRECONDITION_FAILED`。

必须：停服 → 删除队列 → 重启让服务带新参数重建。
而删队列的瞬间，队列里的存量消息**全部丢失**。
所以只能在维护窗口、队列尽量排空的时候操作。

这一步在测试环境毫无问题（队列是空的），在生产上是有损操作 ——
**这类"代码改动本身无害、但上线动作有损"的变更，需要单独的上线预案**，
不能和普通功能发版走同一个流程。

### 防再犯

- 凡是「多生产者向同一队列写入、消费者并发能力有上限」的场景，
  **FIFO 不是公平调度**。要么优先级队列，要么按任务拆子队列，
  要么上调度器做 round-robin。默认 FIFO 等于默认没有调度。
- 业务侧规约：建议单次推送控制在 500 段以内，超大 batch 分批推。
  即使有了优先级队列，单个巨任务仍会独占大量消费者副本。
- reaper 的阈值需要和"队列排空时间"挂钩评估。30 分钟这个数字在
  早期（小 batch）是合理的，在大 batch 出现后就不合理了。
  **超时阈值依赖业务形态，业务形态变了要重新校准。**

### 补记：跨 Pod 的重复触发问题

同一时期还修过一个相关缺陷：多副本部署下，多个 reaper 同时巡检到
同一个 stale task，各自判定失败、各自触发回调 → **上游收到多份重复通知**。

修法是条件 UPDATE + rowcount 判定：

```sql
UPDATE tasks SET status='failed' WHERE id=? AND status='running'
```

只有 `rowcount == 1` 的那个副本知道自己"抢到了"，才去触发回调。
所有多副本都会跑的 cleanup 逻辑都应该用这个模式选 single winner。

## 事故二：progress 永远差 1 —— 事务边界问题

**发生时间**：2026-06-17，**一天内命中 9 个任务**
**影响**：上游反复重试同一批数据，每次都是同样结局

### 症状

所有 segment 都翻译完成了（结果表里译文都写入成功），
但 `task.progress` 永远停在 `total - 1`，不再 +1。

30 分钟后 reaper 判定心跳超时，把任务标记为失败。
上游查询看到 `status=failed`，重试同一批数据 → **同样的结局**。

最典型的一组：同一批 118 段的数据被上游重试了三次，
每次都是**跑满约 75 秒处理完全部 118 段**，然后卡 30 分钟被杀。
译文数据并没丢，丢的是状态转换。

### 根因

处理单条结果时分两步，**两步不在同一个事务里**：

1. 插入结果行（autocommit，立即生效）
2. 另起事务更新父表进度，到总数时才置 done 并触发回调

如果在第 1 步 commit 之后、第 2 步开始之前，进程遇到任何中断
（被驱逐、GC 停顿、心跳超时、收到 SIGTERM），结果是：

- 结果行已持久化 ✅
- 进度没 +1 ❌
- 消息也没 ack（异常跳过了 ack），被 broker 重投
- **重投后进入最致命的路径**：重投的处理逻辑会先做去重检查，
  发现结果行已存在 → 直接返回"已处理" → **永远跳过推进度那一步**

最后一步是死结：进程重启、消息重投都救不了，因为去重逻辑
把唯一能修复进度的路径给挡掉了。

### 为什么之前没暴露

早期单任务 segment 数普遍小于 20，整个任务 1-3 分钟跑完，
中断窗口极短。业务侧开始推 100+ 段的大批量后，
单任务时间跨过了那个边界，问题才稳定出现。

**另外一个隐蔽点**：最后一条最容易踩。因为 ack 之后连接会 idle，
不再发心跳，最容易撞上连接超时。

### 修复

把两步合并进单个事务，从头消除中间态：

```
with tx():
    1. 去重检查（同一事务内 SELECT）
    2. 插入结果行
    3. 父表进度 +1
    4. 若未完成 → 更新任务进度 + 心跳
    5. 若已完成 → 同事务内聚合指标 + 置 done
```

同时确立两条规则：

- **MQ publish 必须在事务之外**。先 publish 再提交事务的话，
  事务回滚后消息已经发出去了，消费者会取到一条指向不存在数据的消息。
  MQ publish 本身是幂等的，失败时可以先标记，由 reaper 补偿重发。
  这也是后来把回调拆成独立队列的原因（见事故三）。
- **去重检查和写入必须在同一事务**。否则两个消费者同时处理
  同一条消息（重投场景）时，都通过去重检查，双双写入。

### 对历史数据

新版本部署后**不会自动修复已失败的任务** —— 它们的状态已经是 failed，
重投和重启都不会再碰。需要手工从结果表聚合指标，直接改父表状态。
当天那 9 个任务是用这个方法救回来的。

**这个坑值得单独记一笔**：修复上线 ≠ 历史数据修复。
任何修状态机的改动，都要单独评估"存量脏数据怎么处理"。

### 防再犯

- 凡是「插入子表 + 更新父表计数 + 可能触发终态」的写入路径，
  **必须在同一事务内**，从设计上消除中间态。
- 写者角色是单写者前提下的唯一真相来源：进度字段只能由它修改，
  且必须原子。
- **外部 IO（MQ publish / HTTP 回调 / 对象存储）永远不要放进数据库事务。**

## 事故三：长连接发病不自愈 —— 救活了 publish 却没救 ack

**涉及版本**：v1.5.5 → v1.5.7 → v1.5.10，三次迭代才收敛

### 症状

第一层症状：写者 Pod 处理完一个 5 段的任务后空闲了 12 分半，
再来消息时 ack 报 `ConnectionResetError(104)`，异常层层嵌套。

第二层症状（更麻烦）：API 服务返回 `503 MQ_UNAVAILABLE`，
`error="ChannelWrongStateError: Channel is closed."`。
内网部署复现不了，公网部署稳定复现。

**关键问题：发病不自愈。** 后续每次请求都用同一个已死的连接单例，
**连续 503 直到 Pod 被手动重启**。而 K8s 的健康检查看的是 HTTP 200，
跟 MQ 状态无关，不会自动杀掉它。

### 根因（三层，逐层剥开）

**第一层：心跳与空闲连接。**
长空闲期间 broker 心跳判超时，或 NAT 关闭空闲 socket。
修复是缩短心跳间隔 + 开启 OS 级 TCP keepalive。

**第二层：真正的原因不在网络，在业务代码占用了消费主线程。**
回调重试的退避序列是 `[0, 30, 120, 600]` 秒，
最坏情况 **13 分钟的 sleep 全跑在消费主线程上**，
心跳事件循环彻底饿死。加了 keepalive 也没用，因为问题不在网络层。

修复是把回调拆成独立角色：写者只做 publish（毫秒级），
立刻 ack 回到事件循环；回调消费者主线程纯做队列 IO，
耗时的 HTTP 重试跑在线程池里。跨线程 ack 必须走
`connection.add_callback_threadsafe`。

> **由此确立的规则**：消息消费主线程不许跑任何可能超过心跳间隔的业务逻辑。
> 心跳 30 秒 → 单条消息处理时间的安全线是 **5 秒**。
> 加新角色时先问"这个工作会不会有 sleep / HTTP / 慢查询"，
> 会的话必须丢线程池 + 跨线程 ack。

**第三层：publish 重连了，但 ack 没有。**
给 publish 加了"检测到死连接 → 快速重连 → 重试一次"的包装后，
日志显示**重连成功、publish 成功**，但紧接着同一条消息的 ack 抛
`ChannelWrongStateError`，整个消费者进程退出重启。

原因是：消费时记下的 channel 引用粘在消息对象上，
重连把客户端持有的 channel 换成了新的，**但消息上的引用还是旧的**。

而这里有个协议层面的硬约束：**AMQP 的 delivery_tag 是 channel 作用域的**。
就算把 ack 改走新 channel，新 channel 也认不出这个 tag ——
**客户端层面没法"修"这件事。**

正确的处理是**识别后放弃**：ack/nack 路径 catch 连接丢失类异常，
记一条 warning 就返回。理由是：

1. broker 在消费者断连时会**自动重投未 ack 的消息**
2. 老 channel 的 tag 在新 channel 上无法 ack，这是协议规定
3. 调用方拿到这个异常也无事可做
4. 结果表上有唯一约束（任务 ID + 段序号），重投不会双写

**消息不丢，只是白白重启一次 + 重跑一次 LLM。**

### 为什么三层要分开修

这不是"一开始没想清楚"，而是每一层都被上一层遮住了：

- 第一层修完（keepalive），故障频率下降，看起来好了
- 过一段时间又出现，才发现是业务代码占主线程（第二层）
- 第二层修完，重连逻辑上线，暴露出第三层（重连只覆盖了 publish）

**日志里有价值的线索**：每次连接抖动都会打印完整连接串，
而连接串里带着 broker 密码 —— 这条日志被日志采集系统长期保存、
多人可读。修复方式是把 URL 里的凭证部分替换成 `***` 再输出，
并把脱敏逻辑抽成命名 helper（而不是各处 inline 正则，那样容易漏）。

> 由此确立的规则：**凡是带 `user:password@` 形式的 URL
> （不止 AMQP，还有数据库连接串、对象存储预签名 URL），进日志前必须过脱敏。**

### 防再犯

- **"长连接 + 单例客户端"的资源，必须设计成发病后能自愈。**
  心跳只是降低发病概率，自动重连是发病后的兜底，两者缺一不可。
- 但自愈策略要按角色区分，不能一刀切：
  - **无状态 worker**（消费者/写者/回调）→ 连接丢失直接退出，
    让编排层重启它。重启无副作用。
  - **API 服务** → 不能退出（会让所有用户看到 502），
    必须用"重连 + 重试一次"的包装，失败才向上返回错误。

  这个区别是有代价换来的：早期把"连接丢失就退出"的策略
  也套在 API 服务上，结果是所有在线用户一起掉线。
- 安全标志不能写死，要绑请求。曾经把 cookie 的 `Secure` 标志
  按"是否生产环境"写死，结果在 HTTP 部署下浏览器直接丢弃 cookie ——
  所有 ajax 正常（走自定义 header），**只有浏览器原生触发的下载路径失败**。
  这类 bug 极隐蔽，因为测试通常只覆盖 ajax 路径。
  修法是让框架信任反向代理的 `X-Forwarded-Proto`，按真实请求协议决定。

## 三条共同规律

复盘完三次事故，有三条反复出现的规律：

**1. 阈值和超时依赖业务形态，业务变了要重新校准。**
30 分钟的 reaper 阈值在小 batch 时代是合理的；
大批量出现后，它变成了"必然误杀"的元凶。
代码没变、配置没变，变的只是输入规模。

**2. 只在异常路径上出现的问题，测试覆盖不到，只能靠设计消除中间态。**
事务边界那个 bug，正常路径和异常路径在故障发生前
表现**完全一致**。这类问题不能靠"多写测试"解决，
要么消除中间态（单事务），要么显式设计补偿逻辑。

**3. 修复要覆盖全部同类路径，不能只修被发现的那一处。**
- 队列优先级：主队列、重试队列、结果队列都要加
- 状态镜像：定时巡检、启动恢复、管理端强制失败，三条路径都要同步
- 连接自愈：publish 和 ack 都要包

**只修被报告的那一条路径，等于把同一个 bug 换个入口再犯一次。**
