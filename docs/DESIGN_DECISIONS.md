# 技术决策记录

按 ADR 的写法：每个决策记录**背景、当时的备选选项、最终选择、理由、代价**。

写代价这一栏是有意为之。任何方案都有代价，只写优点的决策记录
等于没写 —— 后来的人看不到边界在哪，就会在不适用的场景里照搬。

## D1 · 用自建服务，而不是低代码工作流平台

**背景**

项目立项时的原定路线是低代码工作流平台（沿用团队已有技术路线），
理由是搭建快、可视化调整方便。

规模评估后发现这个场景的维度比预期多：

- 数十个 program、**数百个语言对**，每个语言对绑定各自的风格指南与术语表
- Prompt 需要拆成 5 块（通用要求 / 专项规范 / 术语表 / 禁改词 / 标签规则），
  每块要能**独立版本化、独立回滚**
- 存在"生产版本"概念：PM 改完 prompt 要先测试，确认后手动设为生产版本；
  设定之后所有在跑的任务必须继续用**启动时那一版的快照**，不能被中途改掉
- 需要多 PM 并发协作 + 审计日志 + 权限隔离

**备选**

| 选项 | 优点 | 不成立的地方 |
|---|---|---|
| 继续用工作流平台 | 搭建快，非技术人员可调 | 编排是静态的；变量模型承载不了"5 块独立版本 + 运行时锁"；部署形态是单体，无法按队列积压弹性伸缩 |
| 工作流平台 + 外部数据库 | 保留可视化 | 逻辑被拆到两处，一半在工作流、一半在代码，排障时要在两个系统之间来回跳 |
| 自建服务 | 完全可控 | 开发成本高，可靠性问题要自己解决 |

**决策**：自建服务 + 数据库 + 消息队列。

**理由**

判断依据不是"哪个技术更好"，而是**这个场景的核心复杂度在哪**。

这个项目的本质是"每一条 segment 都要按它所属语言对的规则去处理，
而规则本身可以被并发修改"。这是一个**数据一致性问题**，
不是流程编排问题。工作流平台擅长的是后者。

**代价**

- 开发量大幅上升：API、前端、队列、部署、监控全部自己来
- 失去低代码的可视化调整能力，改流程要发版
- 可靠性问题全部自负 —— 后面三次事故基本都在这个代价里

**后来验证**

队列饥饿、事务边界这两个事故，如果用工作流平台，
平台层面确实会替我们挡掉一部分。但反过来，"生产版本运行时锁"
和"per-program 规则注入"这两件事，在工作流里做不到。
**用平台的可靠性换场景适配性，这笔交易在规模上来之后是划算的。**

## D2 · 按 batch 大小分档的优先级调度

**背景**

队列饥饿事故。详见 [`INCIDENTS.md` 事故一](INCIDENTS.md)。

**备选**

| 选项 | 评价 |
|---|---|
| 加大消费者副本数 | 治不了本。队列顺序不变，小任务依然排在后面 |
| 按任务拆子队列（每任务一个队列） | 顺序问题解决了，但队列数量随任务数增长，broker 开销和运维复杂度都上去了 |
| 调度器做 round-robin | 需要在应用层维护待处理任务列表，多副本场景下又要引入分布式锁 |
| **broker 原生优先级队列** | 顺序由 broker 保证，多副本下依然成立，应用层只负责打优先级 |

**决策**：broker 原生优先级队列 + 按 batch 大小分档。

**理由**

关键在于**顺序保证发生在哪一层**。应用层排序在多副本消费时会失效
（每个副本各排各的），必须由 broker 统一维护才能保证全局有序。

分档而不是按段数线性映射，是因为优先级只影响**相对顺序**，
不需要精确的数值差异 —— 5 档足够表达"小任务优先"这个意图。

**代价**

- 大任务完成时间后移 14%（实测数据见事故复盘）
- 上线动作有损：已有队列不能加 `x-max-priority` 参数，
  必须删队列重建，存量消息会丢，只能等维护窗口
- 需要业务侧配合控制单次推送规模（建议 ≤ 500 段），
  否则单个巨任务仍会独占大量消费者

## D3 · 消息队列选 RabbitMQ

**背景**

从单机线程池迁到独立 broker 时做的选型。

**备选**

| 选项 | 适合的场景 | 不匹配的地方 |
|---|---|---|
| Kafka | 高吞吐、事件溯源、可重放 | 分区 + 偏移量模型对"每条消息独立确认"这件事更绕；本场景是低吞吐高可靠，用不上它的吞吐上限 |
| RabbitMQ | 需要 ack / retry / DLQ 开箱即用 | 吞吐上限低于 Kafka（本场景不需要那么高） |
| Redis Streams | 已有 Redis，想简单 | 生态最弱，监控和运维工具要自己拼 |
| 云托管 MQ | 不想自己运维 broker | 团队当时没有可用的云资源配额 |

**决策**：RabbitMQ。

**理由**

这个场景的消息特征是：**单条小（几 KB）、要求可靠重投、
要求可见性超时、要求死信队列**。这正好是 RabbitMQ 的主场。

选型时问的一个关键问题：**单任务最多 2000 条 segment，
假设同时跑 5 个任务就是 1 万条在途消息，broker 顶不顶得住？**
RabbitMQ 在几万条级别毫无压力，不需要为吞吐上限付复杂度成本。

**代价**

- broker 自身的运维（集群、镜像队列、磁盘告警）要自己管
- 消费主线程的阻塞问题需要自己处理（这是事故三的根源之一）
- 队列声明参数不能改，改就要删队列重建

## D4 · 把流水线拆成三个角色、三条队列

**背景**

最初的实现是单进程：API 收到请求 → 进程内线程池 → 直接调模型 → 写库。
跑得通，但有两个问题：无法按负载弹性伸缩；慢环节会拖住快环节。

**备选**

| 选项 | 问题 |
|---|---|
| 单队列，一个消费者角色全包 | 模型调用（9 秒级）、数据库写入（毫秒级）、HTTP 回调（可能 13 分钟）混在一起，最慢的环节决定整体吞吐 |
| 两队列（任务 + 结果） | 回调仍在写者主线程里，事故二就是这么来的 |
| **三队列（任务 / 结果 / 回调）** | 慢路径彻底隔离，代价是消息链路变长，排障要多看一个环节 |

**决策**：三队列 + 四角色
（生产者 / 消费者 / 写者 / 回调者），各自独立部署。

**理由**

拆分依据是**耗时量级**：

| 环节 | 耗时量级 | 伸缩需求 |
|---|---|---|
| 接收与校验 | 毫秒 | 按 CPU 伸缩，2-6 副本 |
| 模型调用 | 秒级（实测单段平均 9 秒） | **按队列积压量伸缩，1-50 副本** |
| 数据库写入 | 毫秒 | 固定 1-2 副本 |
| HTTP 回调 | 秒到分钟级（带退避重试） | 固定副本 + 内部线程池 |

**只有模型调用这个环节需要弹性伸缩**，其他三个固定副本就够。
把它们解耦出来，弹性伸缩策略才能针对性地加在需要的地方。

**代价**

- 消息链路变长，一个任务的状态要跨三个队列追踪，
  出问题时排查路径更长
- 幂等要求提高：任何一环重投都不能导致重复写入
- 部署单元从 1 个变成 4 个

## D5 · 写结果与推进度必须在同一事务

**背景**

事故二。详见 [`INCIDENTS.md`](INCIDENTS.md)。

**备选**

| 选项 | 问题 |
|---|---|
| 两步各自提交 | 中间态无法消除，任意中断都会造成进度永久卡住 |
| 起个补偿任务定期扫描修复 | 补偿逻辑本身要处理"哪些是真卡住、哪些只是慢"，判断成本高，而且补偿期间用户看到的是错的状态 |
| **合并单事务** | 从设计上消除中间态 |

**决策**：合并单事务。

**理由**

**能靠设计消除的中间态，不要靠补偿逻辑兜底。**
补偿逻辑是第二套状态机，它自己也会出 bug，而且出 bug 的时候更隐蔽。

**代价与配套规则**

- 事务范围变大，持锁时间变长（本场景单事务只涉及两条 UPDATE，可接受）
- 必须确立配套规则：**MQ publish / HTTP 回调等外部 IO 绝不放进事务**。
  先 publish 后提交的话，事务回滚后消息已经发出去了，
  消费者会取到指向不存在数据的消息。
- 去重检查必须和写入在同一事务，否则两个消费者同时处理重投消息时
  会双双通过检查、双双写入。

## D6 · 标签保真用代码校验，不靠 Prompt 约束

**背景**

译文要回写进下游翻译系统渲染，所以译文里的行内占位符必须与原文对应。

**备选**

| 选项 | 问题 |
|---|---|
| Prompt 里叮嘱模型"保持标签一致" | 模型会遵守大部分时候，但**不保证**。而这个场景 100 条里有 26 条标签对不上（实测数据） |
| Prompt 约束 + 代码校验 | 双保险 |
| **纯代码校验 + 不通过就重译** | 确定性最高 |

**决策**：Prompt 里说明规则（引导模型做对），
但**判定完全由代码负责**，校验不通过一律标为需要重译。

**四条校验约束**

| 约束 | 说明 |
|---|---|
| 数量一致 | `{1}{2}` 不能在译文里变成 `{2}` |
| 编号集合一致 | 数量对但编号变了同样不接受 |
| 开闭配对一致 | `<b>...</b>` 的嵌套结构不能被破坏 |
| 转义形式一致 | 原文是 `&amp;` 就不能在译文里变成 `&` |

**位置可以变** —— 目标语言语序不同是正常的。
所以比较的是集合与结构，不是顺序。这一点很容易写错：
如果按顺序逐个比对，所有语序不同的语言（日语、德语）都会被误判为不合格。

**理由**

判断"格式对不对"是一个**确定性问题**，有唯一正确答案，
不需要模型来判断。让确定性的事情走代码，让模型专注在它真正擅长的地方
（语义与语气）。

顺带一个收益：校验结果是结构化的明细（哪条约束失败），
可以直接作为重译的输入，也能作为指标上报。

**代价**

- 需要为每种标签语法写解析器（数字占位符 / printf 风格 / XML 风格）
- 校验失败会触发重译，增加模型调用成本（但比交付废译文便宜得多）

## D7 · 上下文窗口用滑动窗口 + 显式标记

**背景**

上游给的是逐句机器译文。逐句独立调用模型会断开指代和语气。

**备选**

| 选项 | 问题 |
|---|---|
| 整篇文档一次性送进去 | 超上下文长度；且模型会对整篇都做改写，不只是目标句 |
| 逐句独立 | 指代丢失（"它"指谁？），语气不连续 |
| **滑动窗口（前后各 N 条）+ 标记目标句** | 需要控制 token 成本 |

**决策**：滑动窗口，默认前后各 5 条，窗口尺寸可配。

**理由**

窗口里必须显式标记哪一条是目标句（`is_self`）。
缺了这个标记，模型会把上下文里的句子也翻一遍，**造成重复输出**。
这个字段看着不起眼，但它是这个机制能工作的前提。

窗口尺寸不设死，因为它是 token 成本和上下文质量的直接权衡：
prompt 模板本身就很大，窗口每加一条都会显著推高单次调用成本。

**代价**

- 窗口构造在上游入库时一次性算好并快照进消息，
  这样消费者不需要回查数据库。代价是消息体会大一些。
- 窗口大小需要按场景调，没有普适值。

## D8 · Prompt 拆成 5 块独立版本化

**背景**

不同 program、不同语言对的处理规则不同。

**备选**

| 选项 | 问题 |
|---|---|
| 一整块 prompt | 改一处要整体回滚；无法针对性地只调整术语规则 |
| **5 块独立版本** | 管理复杂度上升 |

**决策**：拆成「通用要求 / 专项规范 / 术语表 / 禁改词 / 标签规则」5 块，
各自独立版本化。

**理由**

这 5 块的**变更频率和责任人不同**：
术语表由业务方维护、标签规则由工程维护、通用要求很少变。
拆开之后，改术语表不会影响通用要求的版本历史。

配套机制：**生产版本运行时锁**。任务启动时把当时的 prompt 快照
写进消息，执行期间 prompt 被改也不影响这个任务 ——
否则同一批数据的前半段和后半段会用到不同版本的规则，
结果无法解释。

**代价**

- 版本管理逻辑变复杂（5 块 × 版本 × program 的维度）
- 需要在消息里携带版本引用而不是完整内容（避免消息过大）

## D9 · 双数据库后端（SQLite 紧急回退）

**背景**

生产用 MySQL，但需要一条"MySQL 挂了还能跑"的退路，
以及"开发者不需要装 MySQL 就能跑起来"的路径。

**决策**：抽象一层 DB 接口，支持 SQLite / MySQL 双后端。

**代价与教训**

这个决定带来了不少额外工作量，**主要成本在 SQL 方言差异**：

| 问题 | 表现 |
|---|---|
| 子查询更新 | MySQL 报 1093（不能在同表 UPDATE 里 SELECT 同表），SQLite 没这个限制 |
| 参数占位符 | SQLite 用 `?`，底层 MySQL 驱动把 `%` 当占位符 → `LIKE '%x%'` 直接报错 |
| 列长度上限 | **SQLite 的 TEXT 没有 64KB 限制，MySQL 的有** → 本地测试永远测不出来的类型溢出 |
| 返回值类型 | 两个驱动返回的游标对象不同，`lastrowid` 的取得方式不同 |

**最大的教训是第三条**：应用层校验限制设得比数据库上限还宽，
本地 SQLite 跑得好好的，一到 MySQL 就报"数据太长"。
**应用层的限制必须比数据库层的上限更严格**，
校验应该由应用层先拒绝，而不是让数据库报错、用户看到 500。

**结论**：如果重来一次，可能会选择**统一用 MySQL（含开发环境）**，
只在应急场景保留 SQLite。双后端带来的兼容成本，
在项目中期会持续消耗维护精力。
