# 架构说明

## 一句话

把"接收 → 调模型 → 落库 → 回调"拆成三个角色 + 三条队列，
让模型调用这一段的算力随队列积压量自动伸缩，
同时保证上游可见、失败可重试、超时可标记。

---

## 组件

```
┌──────────────────┐        program / batch        ┌──────────────────────┐
│  上游业务系统     │ ────────────────────────────▶ │  Producer (API 服务)  │
│  (HMAC 签名调用)  │ ◀──────── task_id ─────────── │  - 校验 / 幂等去重     │
│                  │                               │  - 建任务 + 逐段入库    │
│                  │       轮询任务状态              │  - 预算上下文窗口       │
│                  │ ────────────────────────────▶ │  - publish MQ1        │
└──────────────────┘ ◀──────── status ──────────── └───────────┬──────────┘
                                                                │
                                             每条 segment 一条消息（带优先级）
                                                                ▼
                                                    ┌───────────────────┐
                                                    │  MQ1 task         │
                                                    │  x-max-priority=10│
                                                    └─────────┬─────────┘
                                                              │
                                        ╔═════════════════════▼═════════════════════╗
                                        ║         Consumer Pods（N 副本）            ║
                                        ║  伸缩依据：MQ1 队列积压量                   ║
                                        ║  每副本目标积压 ≤ 10 条 · min 1 / max 50   ║
                                        ║  拉一条 → 拼 Prompt → 调模型 → publish MQ2 ║
                                        ╚═════════════════════╦═════════════════════╝
                                                              │ 结果（含失败）
                                                              ▼
                                                    ┌───────────────────┐
                                                    │  MQ2 result       │
                                                    └─────────┬─────────┘
                                                              ▼
                                        ┌───────────────────────────────────────┐
                                        │  Writer（1-2 副本，不伸缩）             │
                                        │  写结果 + 推进度（同一事务）             │
                                        │  任务完结 → publish MQ3                │
                                        └───────────────────┬───────────────────┘
                                                            ▼
                                                    ┌───────────────────┐
                                                    │  MQ3 callback     │
                                                    └─────────┬─────────┘
                                                              ▼
                                        ┌───────────────────────────────────────┐
                                        │  Callback（1+ 副本）                   │
                                        │  主线程纯队列 IO                        │
                                        │  HTTP 回调 + 退避重试跑在线程池          │
                                        └───────────────────────────────────────┘

  MQ1 ──重投超过上限──▶ DLQ ──▶ 消费后把对应 segment 标记为 timeout
```

### 职责与伸缩

| 组件 | 副本 | 伸缩依据 | 职责 |
|---|---|---|---|
| **Producer** | 2-6 | CPU 使用率 60% | 接收校验、幂等去重、建任务、入库、预算上下文窗口、推 MQ1；同时承载管理界面 |
| **Consumer** | **1-50** | **MQ1 队列积压量** | 拉一条 → 拼 Prompt → 调模型 → 推 MQ2 → ack MQ1 |
| **Writer** | 1-2 固定 | — | 拉 MQ2 → 单事务写结果与进度 → 完结时推 MQ3 |
| **Callback** | 1+ 固定 | — | 拉 MQ3 → HTTP 回调上游 + 退避重试 |

**消费者是无状态的**：同一个任务的不同 segment 可以被不同副本处理，
副本挂掉后消息自动重投。这是能弹性伸缩的前提。

**只有 Consumer 需要弹性伸缩。** 其他三个角色固定副本就够 ——
接收是毫秒级 IO、写库是毫秒级、回调瓶颈在对方接口响应。
把伸缩策略只加在需要的地方，比全局弹性简单得多。

### 资源配额参考

| 组件 | requests | limits | 说明 |
|---|---|---|---|
| Producer | 200m CPU / 256Mi | 1000m / 1Gi | HTTP 服务，突发流量需要余量 |
| Consumer | 100m / 256Mi | 500m / 512Mi | **单副本不需要大** —— 它主要在等模型响应，本地 CPU 几乎不占 |
| Writer | 100m / 128Mi | 300m / 256Mi | 数据库写入，内存需求最低 |

消费者副本配大内存是常见误判：瓶颈在**等待**，不在计算。

## 消息契约

### MQ1 · 任务消息（Producer → Consumer）

**每条 segment 一条消息**，不是按任务整批发 —— 这样扩缩容才是按
segment 数量走，而不是按任务数量。一个任务可能只有 3 段，
也可能有 790 段，按任务数伸缩完全失准。

```json
{
  "schema_version": 1,
  "task_id": "batch-2026-06-main-06",
  "program_id": "program-a",
  "segment_index": 42,
  "string_id": "doc1-42",
  "source": "Welcome back, {1}!",
  "mt": "Bienvenido de nuevo, {1}!",
  "context": [
    {"string_id": "doc1-39", "source": "...", "is_self": false},
    {"string_id": "doc1-42", "source": "Welcome back, {1}!", "is_self": true},
    {"string_id": "doc1-45", "source": "...", "is_self": false}
  ],
  "priority": 6,
  "attempts": 0,
  "enqueued_at": "2026-06-22T07:30:00Z"
}
```

几个设计点：

- **`version_id` 而不是完整 Prompt**：5 块 Prompt 内容是几 KB，
  塞进每条消息会让消息体膨胀。消费者用版本引用回查即可。
- **`context` 在上游入库时算好**：消费者拿到的是快照，
  不需要回查数据库，也不需要重新计算窗口。
- **`priority` 同时出现在消息体和 AMQP 属性里**：
  重投时消费者需要从消息体读出优先级重新设置，否则会被降级。

### MQ2 · 结果消息（Consumer → Writer）

成功与失败**走同一条队列**，用 `outcome` 字段区分 ——
让写者统一处理，比开两条队列少一处分支。

```json
{
  "schema_version": 1,
  "task_id": "batch-2026-06-main-06",
  "segment_index": 42,
  "string_id": "doc1-42",
  "outcome": "ok",
  "final_translation": "¡Bienvenido de nuevo, {1}!",
  "evaluation_result": "Y",
  "comment": "",
  "metrics": {
    "tag_ok": true, "term_ok": true, "dnt_ok": true,
    "length_ok": true, "format_ok": true
  },
  "consumer_id": "consumer-pod-3",
  "llm_latency_ms": 1820,
  "finished_at": "2026-06-22T07:30:23Z"
}
```

失败形态：

```json
{
  "outcome": "failed",
  "error": "LLM call timeout (3 retries exhausted)",
  "attempts": 3
}
```

### 队列命名

| 用途 | 队列名 | 优先级参数 |
|---|---|---|
| 任务 | `aipe.task.segment` | `x-max-priority: 10` |
| 任务死信 | `aipe.task.segment.dlq` | — |
| 结果 | `aipe.result.segment` | `x-max-priority: 10` |
| 结果死信 | `aipe.result.segment.dlq` | — |
| 回调 | `aipe.callback.segment` | `x-max-priority: 10` |

**DLQ 不加优先级参数** —— 死信队列只做滞留和人工处理，不需要排序。

## 状态流转

```
上游 POST
   │
   ▼
Producer：
   1. 建任务行（status='queued', progress=0）
   2. 逐段建明细行（status='pending'）
   3. publish MQ1 × N
   │
   ▼
Consumer（任意副本）：
   4. 取一条消息
   5. 明细行 → status='processing'，记录 consumer_id
   6. 调模型（失败则退避重试，最多 3 次）
   7. publish MQ2
   8. ack MQ1
   │
   ▼
Writer：
   9. 取 MQ2
  10. 单事务：写结果 + 进度 +1（未完成时更新心跳）
  11. 若完成 → 同事务置 done
  12. 事务外 publish MQ3（若上游配了回调地址）
   │
   ▼
Callback：
  13. 取 MQ3 → HTTP POST 上游 → 失败指数退避重试
```

上游随时可以用 `GET /api/ingest/batch/<task_id>` 查状态，
看到的就是 `status` + `progress` / `total`。

## 失败与重试

### 单条 segment 失败

| 情况 | 处理 |
|---|---|
| 模型调用网络抖动 / 5xx | Consumer 自己退避重试 3 次 |
| 3 次都失败 | 发 `outcome=failed` 结果，**ack 消息** |
| Consumer 进程崩溃（未 ack） | MQ1 可见性超时到期后自动重投给其他副本 |

**重试用尽后必须 ack，不能 nack。** 让 broker 无限重投的话，
这条消息会在队列里反复转圈，把整个队列堵死 ——
一条注定失败的消息，优先级比它的"完整性"更重要。

### 可见性超时参数

| 参数 | 取值 | 含义 |
|---|---|---|
| 可见性超时 | 8 分钟 | 取到消息后 8 分钟内必须 ack，否则自动重投 |
| 最大重投次数 | 3 | 超过后进死信队列 |
| 死信动作 | 标记 timeout | DLQ 消费者把对应 segment 标记为 `timeout` |

### 任务级超时

单个任务有独立的卡死阈值（生产取 30 分钟）：
若 `updated_at` 在该时间内没有推进，判定任务卡死。

> **这个阈值必须和"队列排空时间"挂钩评估。**
> 30 分钟在小批量时代是合理的，大批量出现后就变成了"必然误杀"。
> 详见 [`INCIDENTS.md` 事故一](INCIDENTS.md)。

### 收尾判定不能只看计数

如果某些 segment 卡在死信队列永远回不来，任务计数就永远差几条。
所以收尾判定要补一条检查：**是否还有非终态记录**。
没有了就强制收尾，并在回调里说明哪些失败了 ——

上游宁可拿到「部分结果 + 失败明细」，也不愿意一直等到超时。

## 为后续接手者准备的说明

### 上下文窗口为什么在 Producer 端算

消费者需要的是目标句前后各 N 条的快照。如果在消费者端算，
每条消息都要回查一次数据库，790 段就是 790 次额外查询，
而且随着文档变化，同一条消息在不同时刻算出不同结果。

**在上游入库时一次算好、快照进消息**，消费者拿到的是不可变的数据。
代价是消息体大一些（约 10 条句子的文本），换来的是幂等性。

### 为什么弹 Consumer 而不是弹其他

| 环节 | 单次耗时 | 是否值得弹 |
|---|---|---|
| 接收校验 | 毫秒 | 不需要，CPU 触发 + 固定副本足够 |
| **模型调用** | **秒级（实测单段平均 9 秒）** | **值得** —— 这是唯一的真实瓶颈 |
| 数据库写入 | 毫秒 | 不需要，2 副本只为高可用 |
| HTTP 回调 | 秒到分钟 | 不需要，瓶颈在对方 |

判断依据：**这个环节的耗时是否显著大于其调度开销。**
模型调用 9 秒 vs 容器启动 10 秒，弹性伸缩的收益是正的；
数据库写入 1 毫秒 vs 容器启动 10 秒，伸缩纯属浪费。

### 上线顺序

每一步都有通过条件，不要跳步：

| # | 动作 | 通过条件 |
|---|---|---|
| 1 | 部署 Producer × 2 + Writer × 1，**先不部署 Consumer** | 健康检查双 200 |
| 2 | 上游试推 1 条 segment 的 batch | 队列有 1 条消息；明细表有 1 行 `pending` |
| 3 | 部署 Consumer × 1 | 消息 30 秒内被消费；结果队列出现 1 条 |
| 4 | 等 Writer 消费掉结果 | 明细行变 `done`；上游查询看到 `done` |
| 5 | 触发回调（如果上游配了） | 上游收到 POST 且签名校验通过 |
| 6 | 灰度：上游推 50 条 | 全部完成 ≤ 2 分钟 |
| 7 | 弹性验证：上游推 5000 条 | 5 分钟内副本数自动上升；队列积压稳定下降 |
| 8 | 故意杀掉一个 Consumer 副本 | 可见性超时后自动重投，任务照常完成 |

第 8 步很多人会跳过，但它是唯一能验证"故障恢复真的有效"的步骤。

### 队列参数变更的上线预案

**RabbitMQ 不允许给已存在的队列追加 `x-max-priority`**，
声明时会报 `PRECONDITION_FAILED`。必须停服、删队列、重建。

而删队列会丢掉队列里的存量消息。所以这类变更：

1. 只能在维护窗口做
2. 尽量等队列排空
3. 要提前确认上游的推送节奏（有没有正在跑的大批量）
4. 要有回滚方案

**代码改动本身无害，但上线动作有损** —— 这类变更要单独走预案，
不能和普通发版混在一起。
